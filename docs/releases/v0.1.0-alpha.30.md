`izzy update` moves an app, or the izzy on your machine, to the newest release and lists what the releases in between removed or renamed, `izzy upgrade` plans the renames your app needs and makes them when you approve, and izzy says when a release is out.

## CLI

- **New: `izzy update`.** In an app's folder it sets the version of the IzzyBlazor package in the project files (and in `Directory.Packages.props`) and of izzy in the app's tool manifest, restores the tool and builds the app. `--to <version>` picks a release other than the newest, `--no-build` skips the build, and `--dry-run`, `--diff` and `--json` show the change first. Outside an app, or with `--global`, it runs `dotnet tool update -g IzzyBlazor.Cli` with the version.
- **`izzy update` ends with what the releases in between removed or renamed,** a line each under its release, such as `Icon.Role → Purpose`, back to alpha.16. A parameter that left several components the same way is one line. With `--json` they are in `changes`. Razor takes an old parameter name without a warning, and the page fails when it opens.
- **New: `izzy upgrade` (Pro)** finds where the app uses them, in its `.razor` and `.cs` files. It prints a plan and writes nothing: each rename it would make, a parameter with its `@bind-` and its `Changed`, and what is left to change by hand, by file and line with what to use instead. `--diff` shows the renames as a diff and `--json` gives the plan as data. `izzy upgrade --apply` makes the renames. It starts from the release `izzy update` moved the app from (kept in `.izzy/upgrade.json` until nothing is left); `--from <version>` names it for an app updated by hand. It reads the markup in a page's `@code` too. It doesn't look for methods, which the build reports, or for the CSS variables and classes a release renamed, which are in that release's notes.
- **izzy says when a newer release is out,** in one line after a command: `IzzyBlazor 0.1.0-alpha.31 is out (this is 0.1.0-alpha.30). To update: izzy update`. It asks nuget.org for the package's versions at most once a day, beside the command, and drops the request when the command ends first. The line is said once a day, on the error stream, to a terminal only: not in CI, with `--json`, in `izzy mcp`, or when the output is read by a script or an editor. `IZZY_NO_UPDATE_CHECK=1` turns it off. A stable izzy is told of stable releases only.
- **`izzy audit` on one page needs no Pro.** With a free account (`izzy login`), each finding of a one-page run has its verdict, with your decisions from `.izzy/audit.json`, and its component, fix and place in your code. The run can also write `tasks.md`, `report.html` and `results.sarif`, and takes `--baseline` and `--fail-on real` or `new`. These needed Pro. Signed out, izzy runs axe and its own checks and lists the findings as they are, and an option that needs the account ends with exit code 4 (it was 3). Several pages in one run, `--site` and `--urls` stay Pro. An account's copy of the catalog now has the audit's pack.
- **New: `izzy audit --recheck <id>`** audits again the page a finding is on, after a fix, and says whether it is fixed, still there (exit code 5) or couldn't be checked. `report.md` prints the id of each finding it shows (ten a group; `results.json` has them all), and izzy finds the page in the newest run in `.izzy/audit/` that has it (`--baseline <results.json>` names another run). An edit that moves the element gives its finding a new id: izzy then says how many findings of the same rule the earlier run lacks, and names one. With `--json` the answer is in `recheck`.
- **New: `audit_page` and `recheck_finding` in `izzy mcp`,** for a coding agent: one page audited, with the findings by verdict and where `report.md` is (`tasks.md` is beside it), and a finding looked for again after a fix. They report and change no code, need a free account and audit one page a call. The skill `izzy agent` writes says when to run them, what each verdict asks of the agent, and that no findings is not a statement of conformance.
- **`izzy audit` traces a finding to your code.** Each finding names the IzzyBlazor component that drew the element, with its docs page, and the fix when the pack knows one, such as `Label` for two Breadcrumbs with one name. With `--run` or `--project` it also has the file and line where the component is written: izzy finds the page's file from its `@page` route and looks in it, its layout and the app's own components they use. One tag is that line; among several it picks the one whose written text (`Label`, `id`) is in the element, and otherwise lists the places. The report, `tasks.md` and `results.json` (`trace` on each finding) carry it.
- **New: `izzy audit --format sarif`** writes `results.sarif` for GitHub code scanning and editors: the real findings and those a person must look at, each on its line, with paths from the repository's root. It needs the app's source (`--run` or `--project`). A finding on a page with no file in the app is left out of it.
- **New: `izzy audit` runs four checks of its own beside axe's.** `target-size` is axe's rule for WCAG 2.5.8, turned on, and izzy then tests where each control it finds takes a click: one with a hit area larger than its box is a false positive. `focus-not-obscured` gives focus to a link or button under a header or footer that stays in place and reports the bar when the page leaves it hidden (2.4.11). `focus-visible-forced-colors` compares a picture of each kind of control before and after it takes focus in forced colors (2.4.7), and `forced-colors-indicator` reports the parts of controls and meters that only a fill draws and nothing draws there (1.4.11). Each page is opened once more for the last two, at the widest width, and the reports list that load as `forced colors`. What izzy measured outright is real; a slight change on focus and a part that disappears need a person. Every report's "Not checked" section says where these checks stop. A baseline made before this release has none of these findings, so they count as new: make a new one.
- **New: `izzy audit --format html`** writes `report.html`, the report as one file to hand to a client: the summary by verdict, each finding with its criterion, verdict and fix, and a picture of the page around each element with the element outlined, in light and in dark. It loads nothing, runs no script, follows the reader's color scheme and prints. A group of findings shows ten elements and counts the rest. The pictures are also files in the run's `pictures` folder, and `results.json` names each finding's file in `picture`.
- **New: `izzy add crud --store http` (Pro)** adds the pages to an app with a `.Client` project, where they run in WebAssembly or Auto. The pages, `I{Model}Store` and `Http{Model}Store` go into the `.Client` project, and the server gets `Data/{Model}Api.cs`: an API at `/api/<models>` over the DbContext or memory, with the pages' sign-in and policies. It sends only the fields the pages show, runs the model's validation, saves only the form's fields, and answers at most 500 rows a request. The grid's search, sort, filters and paging travel in the address and run on the server. The model class must be in the `.Client` project. Before, crud refused an app whose pages run in the browser.
- **Fixed: `izzy add crud --view-policy`** now guards the Excel export too (`{Model}Export.cs`), which asked only for sign-in, and Pro's list, detail and form pages, which ignored it. `--edit-policy` works with `--mode pages` too: the list and detail pages hide New, Edit and Delete from people the policy refuses, and the form page asks for the policy. It was ignored.
- `izzy add crud`: the grid page checks an edit policy with `AuthorizeAsync(user, null, policy)`, which needs no `using`. Pro's form page starts a new record's dates at today, as the grid does (they started at 01/01/0001).
- **Fixed: Scheduler.** In a month, the first appointment under a bar that spans days sat one pixel under the bar, which left it less than the 24 pixels a target needs: the list starts two pixels lower in a week that has bars. In forced colors the line for the current time is drawn (in `Highlight`); it wasn't. `izzy audit`'s new checks found both.
- **Fixed: what `izzy audit`'s new checks found on the docs site, second round.**
  - **ListView, Table, DataGrid with `LoadOnScroll`:** tabbing to the Load more button (the one the keyboard reaches) no longer starts a load. The load put the new items above the button, so focus was out of sight in a list that scrolls. The button loads when it is pressed, and scrolling loads as before.
  - **Lightbox in a Carousel:** an item's focus ring is drawn inside the picture. The carousel's track cut the ring off, in every color scheme.
  - **Table on a small screen:** the heading row has 8 pixels between its lines (it had 4), so the select-all checkbox has a target's room above the sort link under it.
  - **Chart legend:** an item is 24 pixels tall (it was 21).
  - **RangeSelector:** each handle takes the pointer 26 pixels wide, outward from the window, so the two don't share room when the window is at its narrowest.
  - **LinearGauge:** a pointer is drawn in forced colors (in `CanvasText`). It was only a fill, and it disappeared.
- **Fixed: `izzy audit`'s checks, three false alarms.** A control out of sight until it has focus (a skip link, a Load more for the keyboard) passes when focus brings it into sight, scrolled to as Tab scrolls to it; one that stays hidden is still found. The button inside a `<select>` the page styles is measured as its select. A hit area that grows to one side counts (the circle of 24 pixels is tried up to 8 pixels from the control's center). The pack says a RangeSlider's two inputs, which lie on one another and let the pointer through, are a false positive.
- **Fixed: DataGrid's edit dialog and row editing** give a nullable enum column a "None" choice (the field showed the first value and saved none), and a `bool?` column a field: Yes, No or None. It had none, so the column couldn't be edited. The word is `IzzyText.EditNone`.
- **Fixed: `izzy add crud`.** Pro's form page saves an edit of a record whose typed key is `[Required]`; it always said the key was missing. A new record's `DateTime` and `DateTimeOffset` start in UTC, the zone the fields show and read them in, and a field with a time says so in its label ("Opened (UTC)"): a date could start a day early east of UTC. A Guid that isn't the key is shown and not edited on the grid page, as on the form page. A required field named Text or Notes says "Enter text." and "Enter notes.". A second run with `--singular` or `--plural` renames the nav entry the first run wrote. `.izzy/items.json` keeps one entry for a model's crud, the last run's. A run that changes nothing no longer repeats where the records are kept or which properties were left out.
- The component data in IzzyBlazor.Core (`tools/izzy/components.json`) has `root`, `own`, `inside` and `like` for each component that can be drawn alone: the tag and classes that mark its outermost element, the other components it draws inside itself, and those that draw the same element. The trace reads them. A component that takes items is drawn with rows to find them, so a DataGrid's pager is traced to the DataGrid, and a component you wrote inside another (a Button as a Menu's `Trigger`) to your own tag.

## Docs

- **New: Developer Tools,** a docs section for every tool: an overview of what each does and what it needs, the izzy CLI's pages and AI assistants. It replaces "The izzy CLI", and the old addresses redirect.
- **New in Accessibility: Automated and manual checks** draws the line between what a tool settles, what it can only point at and what a person must check. **Component status** lists each component's keys, what the automated audit found on its pages and which screen readers it has been tested with.
- **`izzy audit` has six pages** in the Accessibility section: Audit a page, Verdicts, Reports, Find and check a fix, Audit in a build, and What the audit checks.
